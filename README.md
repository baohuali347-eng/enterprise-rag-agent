# 企业知识库问答 Agent

基于 **LangChain + LangGraph + DeepSeek** 的 RAG 问答系统，语料为飞书帮助中心官方文档（约 400 篇、覆盖企业管理后台/审批/假勤/云文档/多维表格等 10+ 分类）。

```
┌─────────────┐   ┌──────────────┐   ┌─────────────┐   ┌──────────────────┐
│  用户提问    │──▶│  查询改写     │──▶│  意图路由    │──▶│  闲聊 → 直接应答  │
└─────────────┘   │ (指代消解)   │   │ (结构化输出) │   └──────────────────┘
                  └──────────────┘   └──────┬──────┘
                                            │ kb
                                            ▼
              ┌───────────────────────────────────────────────┐
              │              混合检索 + 重排                    │
              │   BGE-M3 向量 ─┐                                │
              │                ├─ RRF 融合 ─▶ BGE-reranker 精排 │
              │   BM25(jieba) ─┘                                │
              └──────────────────────┬─────────────────────────┘
                                     ▼
              ┌───────────────────────────────────────────────┐
              │  相关性兜底（低于阈值 → 拒答并说明知识库边界）    │
              └──────────────────────┬─────────────────────────┘
                                     ▼
              ┌───────────────────────────────────────────────┐
              │  生成（强制编号引用 [n]，只依据资料作答）         │
              └──────────────────────┬─────────────────────────┘
                                     ▼
              ┌───────────────────────────────────────────────┐
              │  反思（幻觉引用/答非所问自检）──不合格──▶ 查询扩展 │
              └──────────────────────┬─────────────────────────┘
                                     ▼
                              输出答案 + 来源
```

## 快速开始

```bash
# 0. 环境：Python 3.12 + uv
# 1. 安装依赖
uv sync

# 2. 配置 DeepSeek API Key（https://platform.deepseek.com 创建）
cp .env.example .env      # 然后编辑 .env 填入 DEEPSEEK_API_KEY=sk-xxx

# 3. 数据管线（爬取 → 解析 → 分块 → 索引）
make pipeline

# 4. 问答
make ui        # Streamlit 界面（推荐，带来源展示与检索链路调试面板）
                # 或手动: uv run python -m streamlit run kb_agent/ui.py
make ask       # 或命令行问答
```

## 技术架构

### 数据管线

| 阶段 | 实现 | 要点 |
|---|---|---|
| 采集 | `kb_agent/crawler.py` | 从帮助中心 `categoryTree` 接口获取站点地图（364 分类 / 2564 文章），按分类关键词筛选 + 热度排序选取 400 篇，遵守 robots.txt、限速、失败重试 |
| 清洗 | `kb_agent/parser.py` | 正文在页面嵌入式 JSON（`window._templateValue`）中，按"版本页签"提取富文本 HTML → Markdown，过滤页脚/问卷等噪音 |
| 分块 | `kb_agent/chunker.py` | **标题层级分块 + 父子文档**：子 chunk（~400 字，带标题路径前缀）做检索，父 chunk（完整章节）送 LLM |
| 索引 | `kb_agent/indexer.py` | 双路：BGE-M3 向量（Chroma）+ BM25（jieba 分词） |

### Agent 图（LangGraph）

节点与边：

- **rewrite**：多轮指代消解，把"它怎么设置？"改写成独立查询
- **route**：结构化输出（pydantic）区分知识库问答 / 闲聊
- **retrieve**：混合检索 + RRF 融合 + 重排；反思重试时带建议做查询扩展
- **relevance**：最高重排分低于阈值 → 拒答，防止用无关内容硬编答案
- **generate**：上下文编号注入，要求答案逐句标注 [n] 引用，只依据资料作答
- **reflect**：LLM 自检（幻觉引用 / 答非所问 / 漏答），不合格触发一次重试（上限 `MAX_RETRY`）
- **decline**：知识库边界外 → 礼貌拒答 + 说明覆盖范围

### 检索

- **BGE-M3**（1024 维，本地 CPU 推理）：语义召回
- **BM25 + jieba**：精确词面匹配（产品名、菜单、报错码）
- **RRF**：排名融合，避免两种分数直接相加的量纲问题
- **BGE-reranker-v2-m3** 交叉编码精排：RAG 效果提升性价比最高的一步

### 评测

`kb_agent/eval/`：

1. **评测集**：按分类分层抽样父文档，LLM 生成"答案确实在该文档中"的问题（文档 id 即真值，检索指标无需人工标注）+ 10 个知识库外问题（测拒答）
2. **检索指标**：recall@1/3/5、MRR
3. **生成指标**：LLM-as-judge 打分忠实度、引用准确率；边界问题拒答率
4. **消融实验**（`make ablate`）：量化每个组件的贡献，见下节

当前结果（详见 `data/eval/report.json`）：

| 指标 | 数值 |
|---|---|
| recall@5 | 1.000 |
| MRR | 0.950 |
| 忠实度 | 0.998 |
| 引用准确率 | 0.980 |
| 拒答率 | 0.900 |

### 消融实验

两组对照，回答"每个组件到底值多少"：

**检索消融**（分块策略 × 检索模式，50 题，文档级命中）：

| 分块策略 | 检索模式 | recall@1 | recall@3 | recall@5 | MRR |
|---|---|---|---|---|---|
| fixed | dense | 0.760 | 0.920 | 0.920 | 0.833 |
| fixed | sparse | 0.700 | 0.960 | 1.000 | 0.826 |
| fixed | hybrid | 0.780 | 0.980 | 0.980 | 0.870 |
| fixed | full | 0.900 | 1.000 | 1.000 | 0.943 |
| hier | dense | 0.780 | 0.940 | 0.940 | 0.853 |
| hier | sparse | 0.800 | 0.920 | 0.960 | 0.866 |
| hier | hybrid | 0.780 | 0.960 | 1.000 | 0.866 |
| hier | **full** | **0.900** | **1.000** | **1.000** | **0.950** |

**生成消融**（LLM-as-judge，50 知识库题 + 10 边界题）：

| 图配置 | 忠实度 | 引用准确率 | 拒答率 |
|---|---|---|---|
| 无反思节点 | 0.980 | 0.980 | 0.900 |
| 完整图（含反思-重试） | **0.998** | 0.980 | 0.900 |

> 结论速读：
> 1. **重排是单点提升最大的组件**：recall@5 两策略均达 1.0 后，重排把 hier 的 MRR 从 0.866 拉到 0.950、recall@1 从 0.78 拉到 0.90——"该找到的都能找到，重排负责把对的排到第一位"，这对下游生成质量影响最大。
> 2. **混合检索比单路更稳**：纯向量 recall@1 0.78、纯 BM25 0.80，融合后 0.78-0.90 且 recall@5 满血，两种召回模式互补。
> 3. **层级分块在文档级小幅占优**（MRR 0.950 vs 0.943）；其更大优势在章节级检索精度（检索单元更聚焦），文档级指标对分块不敏感是诚实结论。
> 4. **反思-重试提升忠实度**（0.980 → 0.998）：发现检索偏差后带建议查询扩展重试一次，把"编造"进一步压到接近 0。

## 面试准备：关键设计决策问答

**为什么按标题层级分块？** 帮助中心文档有天然的 h1/h2/h3 结构，标题边界即语义边界；固定长度切分会把问题和操作步骤拦腰截断。

**为什么父子文档？** 检索要小块（精确、低噪），生成要大块（上下文完整），目标冲突所以拆两层：子 chunk 建索引，命中后取父 chunk 送 LLM。

**为什么子 chunk 带标题路径前缀？** 很多正文是"点击右上角…"，脱离标题无法判断讲什么；前缀让 chunk 自带上下文，两条检索通路都受益。

**为什么混合检索 + 重排？** 向量管语义、BM25 管词面，互补；RRF 解决分数量纲问题；交叉编码器精排比单纯调 top-k 更有效。

**反思循环为什么只重试一次？** 自检不合格多为检索偏差，查询扩展重试一次性价比最高；无限重试会放大延迟且收益递减，重试耗尽后输出答案并附保守提示，保证可用性。

**为什么 404/拒答也要做？** 企业知识库的边界是产品能力的一部分：不知道就说不知道，比编一个像真的答案更可信（幻觉是 RAG 落地的最大障碍）。
