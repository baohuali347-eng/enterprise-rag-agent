# RAG 项目改进记录

## 第 1 步：多轮问答与分块长度（2026-11-04）

### 多轮问答

复现场景：先问“飞书云文档能设置链接有效期吗？”，再追问“它怎么设置？”。

原实现中，检索使用“飞书云文档的链接有效期怎么设置？”，生成和反思却只收到“它怎么设置？”，生成时也没有历史。检索理解了指代，后续节点仍可能失去对象。

现在检索、生成和反思共享独立查询。生成和反思同时获得最近 4 轮已完成对话；即使改写失败退回原问题，也保留历史供理解指代。提示词明确：历史只用于理解问题，事实必须由本轮检索资料支撑。

`ask(query, history=...)` 的 `history` 传入已完成轮次，不重复放入当前问题；兼容旧调用方在尾部放入当前问题的方式。CLI 与 Streamlit 在问答成功后再保存本轮消息。返回值新增 `standalone_query`，界面侧栏展示它，便于定位改写错误。

### 分块长度

原实现只在换行处尝试分块，2000 字的单段会原样变成一个子块；父块的 `PARENT_MAX_CHARS` 只有配置，没有被使用。标题也未计入长度。空正文还可能生成标题块，短子章节合并时会丢失子标题。

现在的约束：

- 子块包含标题前缀，最多 400 字符。
- 父块包含标题前缀，最多 2500 字符，超长章节继续拆分为章节片段。
- 优先按换行或句末切分，超长单段使用字符切分；相邻正文窗口保留 50 字符重叠。
- 极长标题只压缩文本中的展示前缀，完整标题路径保留在父块元数据中，为正文预留空间。
- 空正文不产出分块；合并短子章节保留子标题。

父块首片保留 `doc_id#pN`，后续片段为 `doc_id#pN.sM`。同一文章的 `doc_id` 不变。旧评测的父块真值可能对应已拆分的章节，后续评测需重新核对，不能把旧父块标签直接视为新片段真值。

### 验证范围

运行 `.venv/bin/python -m pytest tests/ -q`：34 项测试通过。图测试实际执行 LangGraph，但用测试替身替代 LLM 和检索器，覆盖首轮、追问、旧历史格式、改写失败、四轮历史窗口及反思重试。它们验证数据传递，不代表真实模型效果已达标。

在内存中重新分块全部 429 份语料，检查长度、ID 唯一性和父子关联：2099 个父块、2931 个子块；最长父块 2497 字符，最长子块 400 字符。固定窗口基线为 2183 块，最长 400 字符。单段、句末和换行切分测试还检查了重叠还原后与输入逐字符一致。

已重建并启用本地两套 Chroma + BM25 索引，逐条校验向量集合的 ID、文本、父子关联与语料一致。新索引在独立目录完成构建及检索检查后才替换原索引。旧索引、旧分块和旧评测已备份到 `data/baselines/20261104-before-step1/`。

本次建库使用 Apple GPU 加速，应用仍默认在 CPU 检索；抽取一条文本对比 CPU 编码与 GPU 建库向量，余弦相似度为 0.99999994。两条问题已通过实际的向量 + BM25 + RRF + 重排运行检查，固定分块的向量检索也可运行。运行检查只验证链路可执行，业务正确性仍需下一步逐题评测。

构建与校验记录分别保存在 `data/index/rebuild-step1.json` 和 `data/index/validation-step1.json`。后续自行重建时运行：

```bash
make chunk index
```

本步骤不调用 DeepSeek，不重新计算旧评测分数。README 中的检索、生成及消融分数已标明为修复前基线。

### 运行检查发现的待验证现象

对“飞书审批如何撤回？”进行实际检索时，首条结果是“管理员设置撤回和编辑消息权限”，重排分约 0.884，超过当前相关性阈值 0.35。这提示仅凭最高分可能无法区分审批撤回和消息撤回。尚未运行答案生成，也没有完成该问题在当前语料中是否可回答的人工标注，因此目前记录为检索偏差候选，不计为已验证的回答失败。下一步应将它纳入评测，核对语料覆盖、前五条结果和最终回答。

## 第 2 步：用户场景评测（2026-11-04）

新增 `kb_agent/eval/datasets/user_scenarios.json`：20 个场景、24 轮，包括直接提问、口语表达、多轮追问、领域内无答案、领域外问题和需澄清问题。题集由本次协作根据原文设计和核对，不是真实用户日志，也没有独立人工验收。可回答题包含原文引用片段及参考要点，并固定语料快照指纹。

新增 `make scenarios-check` 离线校验和 `make scenarios` 实际评测。多轮题使用系统前一轮真实输出，裁判与问答分开计时；逐轮保存节点轨迹及重试内容。成功要求行为正确、关键事实满足、有本轮资料支撑及有效引用。问答错误、裁判错误及被前文错误阻断的轮次分别记录。

52 项测试通过，覆盖数据传递、场景隔离、引用边界、裁判耗时排除、异常处理和成功率口径。实际调用 DeepSeek 完成 24 轮评测及裁判，无执行异常或裁判异常。

本轮：可回答题成功 15/16，误拒答 0/16，整体成功 21/24，正确拒答 6/6，澄清成功 0/2；问答 p50/p95 为 6.13/7.82 秒。分数为小型开发集上的同模型辅助判断，不代表生产准确率。

完整产物在 `data/eval/scenario_runs/20261104-step2-full/`。可版本管理的 [结果摘要](scenario-evaluation-results.md) 和 [评测口径及复现方法](scenario-evaluation.md) 已补齐，旧评测报告未被覆盖。

## 第 3 步：实际失败案例（2026-11-04）

已整理 [3 个失败案例](failure-cases.md)：

- `direct-02`：正确文章的操作章节在 RRF 融合后排第 35，被前 20 候选截断排除，导致漏答。诊断结果保存为独立 JSON，不计入评测成绩和延迟。
- `ambiguous-01`：无历史的“它怎么设置？”被低相关性分数直接导向越界拒答，缺少先澄清对象的分支。
- `ambiguous-02`：未明确权限对象，高分检索直接触发两套权限操作说明，事实可被资料支撑但没有先确认用户意图。

每个案例包含实际执行的问题、预期、实际表现、检索或图节点证据、改进建议及验收方法。第 3 步时这些建议尚未实施；后续实现及新一轮成绩见下文，原始失败记录和分数保留。

## 第 4 步：澄清及操作章节召回修复（2026-11-04）

新增 `clarify` 路由及终止节点，不明确对象时先问必要信息；已有明确功能或充分历史时继续知识库问答。用户补充后的消息按正常多轮改写处理。分类使用枚举约束，并保留路由原因供调试。

完整检索模式将 RRF 后的重排候选预算由 20 改为可配置的 40，最终仍返回最多 5 个去重父块。修改前的本地候选池对照确认：之前 RRF 排第 35 的群成员导出操作章节能进入最终第 4 条。同步修复重复文本按文本反查 ID 导致来源错配的问题，改为分数与输入 ID 直接对应。此次分块和索引未变。

第一版路由让已明确的消息撤回时限问题被过度澄清，该轮 23/24 的完整结果及源码快照已保留。收紧为“功能对象明确时先回答一般方法”后，重新完整运行原开发集，最终 24/24 轮通过，回答 16/16、澄清 2/2、正确拒答 6/6。未将不同版本的较好逐题答案拼接。

另在修改前固定了 8 场景、10 轮补充检查，覆盖新表达及澄清后继续问答；单独运行后 10/10 通过。两套题均为同一协作助手设计的小型模型辅助评测，不是独立人工测试集或线上日志。

68 项测试通过。可回答题成功率的改善伴随 CPU 重排计算增加，原开发集问答 p50/p95 从 6.13/7.82 秒升至 8.20/12.87 秒，性能成本已保留在 [完整修复对照](fix-validation.md)。原基线、第一版、最终版及补充检查的运行目录相互独立。
